# Migration Strategy — MariaDB `kran_website` → PostgreSQL

**Existing:** MariaDB/MySQL, schema `kran_website`, JDBC in `DataSource.xml` / Hikari in `Database.java`  
**Target:** PostgreSQL per-service databases (see PostgreSQL_Database_Architecture.md)

---

## Phase 0 — Discovery

1. Export full MariaDB DDL + row counts: `mysqldump --no-data`, `SELECT table_name, table_rows FROM information_schema.tables`.
2. Freeze Hibernate entity list (19 tables) as migration scope.
3. Identify charset/collation issues (UTF-8 assumed).
4. Catalog file paths in `kran_uploads/` for resume/image migration to object storage.

---

## Phase 1 — PostgreSQL provisioning

1. Create databases: `kran_auth`, `kran_content`, `kran_catalog`, `kran_media`, `kran_careers`, `kran_engagement`, `kran_notification`.
2. Create service roles: `{service}_app` (DML), `{service}_migrate` (DDL for Flyway CI only).
3. Apply Flyway `V001__baseline.sql` per database from `postgresql/ddl/`.

---

## Phase 2 — Schema mapping rules

| MariaDB | PostgreSQL |
|---------|------------|
| `INT AUTO_INCREMENT` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` + insert explicit id on migrate |
| `DATETIME` | `TIMESTAMPTZ` (store UTC; app Asia/Kolkata) |
| `DOUBLE` mobile | `VARCHAR(20)` or `NUMERIC` if purely numeric |
| `VARCHAR(200000)` | `TEXT` |
| Mixed-case columns | snake_case target; ETL column map CSV per table |
| `TINYINT(1)` flags | `VARCHAR(1)` or `BOOLEAN` with transform |

---

## Phase 3 — ETL execution

**Tooling:** AWS DMS, pgloader, or custom Spring Batch / Python scripts.

Recommended order (respect logical deps **within** each DB):

1. **catalog:** category → casestudy, kran_*, project_product  
2. **content:** news, banner, blog, kran_timeline  
3. **media:** gallgroup → gallery  
4. **careers:** careers → application_request, submitted_resumes  
5. **engagement:** contacts, comments  
6. **notification:** mail_setup  
7. **auth:** bootstrap admin_user (not from legacy table)

**ID preservation:** `SET IDENTITY INSERT` equivalent — after bulk load, `SELECT setval(pg_get_serial_sequence('news','id'), (SELECT MAX(id) FROM news));`

---

## Phase 4 — File asset migration

| Legacy | Target |
|--------|--------|
| `resume_path` filename | S3/Azure Blob URI in `resume_path` |
| `image_path` relative | CDN URL or bucket key |
| Validate orphan files | Report only; do not block cutover unless business requires |

---

## Phase 5 — Validation

| Check | Method |
|-------|--------|
| Row counts | Per-table MariaDB vs PostgreSQL |
| Spot PK samples | 100 random ids per table |
| FK integrity | Within-service only |
| Public smoke | Compare API JSON to legacy JSP output |
| Admin CRUD | Round-trip create/edit/deactivate |

---

## Phase 6 — Cutover

| Strategy | Description |
|----------|-------------|
| **Recommended** | Strangler: new React app reads PostgreSQL; legacy WAR read-only; dual-write **avoid** |
| Freeze window | Stop admin edits on legacy; final delta sync; DNS to new stack |
| Rollback | Keep MariaDB snapshot 30 days; revert gateway routes |

---

## Phase 7 — Decommission

- Archive MariaDB dump to cold storage.
- Remove credentials from legacy `DataSource.xml` in repo (separate security task).
- Document completion in SRS revision history.

---

## Flyway vs Liquibase

**Recommendation:** Flyway — one `flyway_schema_history` per database, versioned SQL in repo `src/main/resources/db/migration`.

Liquibase acceptable if org standard; same ownership rules apply.
